# Mahjong v1 — Plan 3: Expo App + Art

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `@mahjong/app` — the Expo React Native client: original SVG tile art, four screens (Home, Lobby, Table, Results), landscape game table, animations, connected to the Plan 2 server.

**Architecture:** One zustand store is the app's single source of truth, fed exclusively by server messages (`lobby`, `view`, `hand-result`, `seat-status`, `session-end`, `error`, `emote`); screens render the store and dispatch intents through a thin colyseus.js wrapper. All tile art is a data-driven `TileFace` SVG component — 42 faces from one design-token set, so a future theme is just a token/asset swap. Visual work has manual device checkpoints; all pure logic (store, reducers, layout math, tile data) has jest tests.

**Tech Stack:** Expo (latest SDK, default template with expo-router), TypeScript, zustand, colyseus.js ^0.16, react-native-svg, react-native-reanimated, expo-screen-orientation, @expo-google-fonts/noto-serif-tc, @react-native-async-storage/async-storage, expo-crypto, jest-expo.

**Spec:** `docs/superpowers/specs/2026-08-16-mahjong-app-design.md`
**Depends on:** Plan 2's wire protocol (`packages/server/README.md` once built; tables in Plan 2 Tasks 5/6/8/9). **Reconcile against the real README before executing.** Engine types (`PlayerView`, `Action`, `TileKind`, …) import from `@mahjong/engine`.

## Global Constraints

- Plan 1 global constraints still apply. Windows dev machine: Android testing via Android Studio emulator or a physical device with Expo Go; no iOS work in this plan.
- **The store is written by server messages only.** No screen mutates game state locally; an optimistic UI change is limited to disabling buttons while an action is in flight.
- Every string the user sees lives in `src/strings.ts` (one place; localization later).
- Every color/dimension/radius/duration lives in `src/theme/tokens.ts`. No literal colors or magic layout numbers in components.
- Server URL comes from `process.env.EXPO_PUBLIC_SERVER_URL`, default `http://10.0.2.2:2567` (Android-emulator loopback to the host machine).
- Engine/bot/server suites keep passing: run root `pnpm test` before every commit.

- `tileData.ts` produces `FACE_DATA: Record<TileKind, FaceData>` where

```ts
export type FaceData =
  | { kind: 'dots'; circles: { cx: number; cy: number; r: number; color: 'suitBlue' | 'suitRed' | 'suitGreen' }[] }
  | { kind: 'bamboo'; sticks: { x: number; y: number; color: 'suitGreen' | 'suitRed' }[] }
  | { kind: 'glyph'; chars: string[]; colors: ('inkPrimary' | 'suitRed' | 'suitGreen' | 'suitBlue')[] }
  | { kind: 'frame' };  // white dragon: empty bordered frame
```
  Coordinates are in a fixed 100×140 viewBox. Content: dots use the traditional circle arrangements per rank (1 = one large center circle; 2 = vertical pair; 3 = diagonal; 4 = corners; 5 = quincunx; 6 = 2×3; 7 = diagonal-3 over 2×2; 8 = 2×4; 9 = 3×3); bamboo use traditional stick stacks (1 = single ornamental stick for v1); characters `1w–9w` = `['一'…'九', '萬']` with numeral `inkPrimary`, `萬` `suitRed`; winds = 東/南/西/北 in `inkPrimary`; dragons = 中 `suitRed`, 發 `suitGreen`, 白 = `frame`; flowers `f1–f8` = 梅蘭菊竹春夏秋冬 in `suitRed`/`suitGreen` alternation with the flower index numeral small in a corner.
- `TileFace.tsx` produces `TileFace({ tile, size }: { tile: TileKind; size?: number })` — pure SVG in the 100×140 viewBox scaled to `size` (default `tokens.tile.w`), fonts via `NotoSerifTC_700Bold`.

### Task 4: Device identity, connection wrapper, and the store

**Files:**
- Create: `src/net/deviceId.ts`, `src/net/connection.ts`, `src/state/store.ts`, `src/strings.ts`
- Test: `test/store.test.ts`

**Interfaces:**
- `deviceId.ts`: `getDeviceId(): Promise<string>` — AsyncStorage-persisted `expo-crypto` `randomUUID`.
- `store.ts` (zustand):

```ts
export interface RoomLobby { code: string; hostPlayerId: string; config: RoomConfig; seats: SeatPublic[] }
export interface GameStore {
  connection: 'idle' | 'connecting' | 'connected' | 'error';
  errorMessage: string | null;
  identity: { playerId: string; name: string } | null;
  lobby: RoomLobby | null;
  view: PlayerView | null;
  seatStatus: Record<number, boolean>;      // connected flags during game
  lastHandResult: { result: HandResult; scores: number[] } | null;
  standings: { seat: Seat; name: string; score: number }[] | null;
  emotes: { seat: Seat; emote: string; id: number }[];
  pendingAction: boolean;                    // an action is in flight → disable inputs
  // message reducers (called by connection.ts):
  onMessage(type: string, payload: unknown): void;
  // intents (called by screens; delegate to connection.ts):
  createRoom(name: string): Promise<void>;
  joinRoom(code: string, name: string): Promise<void>;
  send(type: string, payload: unknown): void;
  playAction(action: Action): void;          // sets pendingAction; cleared on next view
  leaveRoom(): void;
}
```
- `connection.ts`: colyseus.js `Client(EXPO_PUBLIC_SERVER_URL)`; `create('table', {playerId, name})` / `joinById(code, …)`; fans every `onMessage` into `store.onMessage`; on `onLeave` with error → `connection: 'error'` + auto-rejoin attempt by code (3 tries, backoff) since the server restores seats by `playerId`.

- [ ] **Step 1: failing tests** — pure reducer tests (no sockets): feed `onMessage('lobby'|'view'|'hand-result'|'seat-status'|'session-end'|'error'|'emote', fixture)` sequences; assert store fields, `pendingAction` clears on `view`, `error` populates `errorMessage` without clobbering `view`, emotes capped at last 5.
- [ ] **Steps 2–5:** fail → implement (connection wrapper is thin enough to leave to integration testing in Task 8) → pass → commit `feat(app): store, message reducers, connection wrapper`
